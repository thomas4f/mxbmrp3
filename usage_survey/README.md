# Usage survey

A static dashboard derived from the plugin's [Aptabase](https://aptabase.com) telemetry.
[`REPORT.md`](REPORT.md) (plus the SVG charts in [`charts/`](charts/)) is generated by
[`tools/analytics_report.py`](../tools/analytics_report.py) from the **monthly exports**
Aptabase provides, merged with the rollup described below. The raw exports are **not**
kept in the repo - only the generated report and that rollup are.

## Regenerate

1. In Aptabase, export **just the newest month** (CSV or Parquet - the tool reads either,
   and they can be mixed in one run; Aptabase withdrew the Parquet export at one point).
   Every earlier month is already in [`rollup/`](rollup/).
2. Run the generator (Windows `&`, or one command per line):

   ```
   python3 tools/analytics_report.py path\to\mxbmrp3release2026XX.csv
   ```

   Pass any number of files (or a glob) - they're merged and de-duplicated, and a day the
   export covers replaces that day in the rollup, so re-running a month you already have
   is safe. The report's data window is taken from the data itself, not the filenames.
   Output defaults to `usage_survey/`; override with `--out`.

3. Commit the regenerated `usage_survey/REPORT.md`, `usage_survey/charts/*.svg` **and**
   `usage_survey/rollup/*`. Do **not** commit the raw export (both `.csv` and `.parquet` are
   git-ignored).

## The rollup (why you only need the newest export)

A run knows only about the exports you hand it, so before `rollup/` existed, regenerating
meant re-supplying every month since reporting began - and a run with only the latest
export silently produced a 7-day report where the last one covered 73 days, with no error
anywhere. [`rollup/`](rollup/) is the tool's memory: after each run it writes back a small,
de-identified digest of everything it has seen (`manifest.json` plus one gzipped CSV per
month, and one for the per-install snapshot), and reads it on the next run.

- **It is a digest, not the export.** Only what an aggregate can be rebuilt from is kept:
  launches as (hour, install, game, version, coverage bits) with a repeat count, sessions
  as (hour, version, duration), crashes with their fault fields, and one row per install
  holding its latest ping. `user_id`, `session_id`, locale, region and the per-launch props
  of every launch that is not an install's latest are dropped - ~650 MB of CSV becomes
  ~5 MB. `install_id` is replaced by a one-way hash of itself.
- **The window only grows.** Re-running with one month does not shrink the report.
- **Adding a field the report reads per launch means storing it too.** A launch that has
  aged into the digest no longer carries its props, so anything asked per-launch must be
  a stored column (`cov` is how the coverage table survives this). The `--selftest`
  round-trip asserts it: the same data through the rollup must produce the same REPORT.md
  as the raw export, byte for byte, so a field that did not survive fails the gate.
- **To rebuild it,** delete `usage_survey/rollup/` and re-run with every export you still
  have. `--no-rollup` ignores it for a one-off run without updating it.

Requires `pandas`; `pyarrow` only for Parquet input (`python3 -m pip install -r tools/requirements.txt`). The SVG
charts have no extra dependency (`tools/analytics_svg.py`). Run `--selftest` to exercise the
whole pipeline on synthetic data with no export on hand.

## What it measures (and how to read it)

It opens with a short **Highlights** TL;DR (reach, platform, repeat use, top HUD, stability),
then the detail: what matters to the **plugin dev / users** (installs, activity per game,
versions, geography, OS, repeat usage, feature/HUD/widget adoption) and to the **upstream game
dev** (crash rate, crash categories, the most common crashes with triggers + workarounds, and
an uncatalogued tail). Each crash is listed once - named crashes by name, the rest by fault
signature - so the two crash tables don't overlap. Count charts label each bar with its count
and share; adoption charts label with share then count. Two things are worth internalising:

- **`install_id`, not `user_id`.** Aptabase's `user_id` is a privacy-preserving hash that
  **rotates daily** (~8 distinct ids per real install in the sample data), so it badly
  over-counts installs. Every install-level metric keys on the plugin's own stable
  `install_id` from `string_props`.

- **Coverage-aware by design.** Telemetry landed in **1.26** and was refined through **1.27**,
  so early builds omit fields (e.g. `os_version`). Rather than average over a denominator that
  doesn't include those events, each feature/geo/OS metric reports the value **and** how many
  installs actually sent the field. The *About this data* section spells out the gaps per
  release line, so a partial rollout is never mistaken for a real trend.

- **A gap in the data is drawn as a gap.** Ingestion stops when the Aptabase account's
  monthly event quota runs out, and the export then has no rows for those hours - which is
  not the same fact as "nobody played". The generator finds those stretches from the data
  (`collection_gaps`: hours holding under 5% of what the surrounding week's hours hold, run
  together, ignoring anything under 3 h so a quiet night is not mistaken for an outage),
  keeps those days on the axis, shades them, and **breaks every line across them** rather
  than joining the days either side. A day a gap ate more than a tenth of is left blank for
  the same reason a partial export day is: its total is real but not comparable. Every
  average divides by the days actually observed, and the header states both numbers
  (*"68 days, 51 observed"*). The one thing the report will not do is interpolate.

- **Achievements are Steam-style global stats.** Since 2.21.0 the launch ping carries every
  achievement at tier 1 or higher by its catalogue id (`ach_<id>` = tier), beside two totals
  (`ach_pct`, `ach_unlocked`). The section shows how far installs get, how many they hold,
  and the share of reporting installs holding each one; rows are labelled from
  [`docs/achievements.md`](../docs/achievements.md), which is generated from the plugin's
  own catalogue - which is also where the row icons come from, so neither can drift from
  what the plugin ships. The bars are
  **split by tier**: the ping sends the tier reached as the value, so bar length is who
  holds an achievement and the split is how far they have taken it - an achievement
  most people have and one most people have *finished* are the same bar otherwise. Tier
  is ordinal, so it takes one hue stepped light-to-dark (not four categorical colours,
  and not the literal metals - silver and platinum are within a few percent of each
  other, and platinum is nearly the light background). The denominator is installs that
  report the totals at all - a version from before the feature is silent, not at zero.
  Only achievements somebody holds are charted - the rest are one line, not a screen of
  empty bars. **Hidden achievements are never charted or named**: the plugin keeps a few unlisted
  until a player stumbles on one, and a public report that names it spoils exactly what
  it is for. They are rare by construction, so the "rarest" line is where they surface
  first - it named one before this filter existed. The flag is read off the `## Hidden`
  heading in that same generated doc, and the selftest fails if that section stops being
  found. The per-install *totals* still include them, as the plugin sent them, which is
  why a progress figure can read over 100%. **Plugin 1.30.0 is excluded** (`ACH_MIN`, the same shape as
  `CRASH_MIN`): it built the ping before the save file had loaded, so it reports a hard
  zero, which a "report the field at all" denominator cannot tell from a player who has
  genuinely earned nothing. 1.30.1 moved analytics after the stats load. The report does
  not narrate the exclusion: the build it describes is nearly gone, and a standing
  paragraph about a fixed bug outlives its usefulness faster than it retires itself.

- **Adoption is per-game.** HUDs/widgets/features are game-specific (ECU & Tyre Temp are GP
  Bikes only; FMX/Records are MX Bikes only), and the plugin only emits a flag where that
  item exists. So the adoption charts are computed for the **primary (most-installed) game**
  - otherwise a GP-Bikes-only widget's rate would sit next to MX-Bikes rates over a totally
  different base. Within that one game, a flag reported by fewer installs (a newer feature) is
  shown as *"N of M"* so its smaller base is explicit - and one reported by fewer than
  `MIN_ADOPTION_BASE` installs gets no bar at all, only a line naming it and its base. A flag
  a couple of dev builds report is a 100% adoption rate by arithmetic, and ranking by share
  puts it straight to the top of the chart.

## Crash linkage

Crash events carry a faulting `module+offset` and the game build hash. The generator joins
these against [`crash_analysis/known_game_crashes.json`](../crash_analysis/known_game_crashes.json)
(the machine-readable crash registry) on `(game_build, offset)` and annotates matched crashes
with their catalogued name + whether a workaround exists. When a new build is catalogued there,
re-running this tool automatically classifies more of the crash tail.

Crash stats are computed over plugin **1.27.5+ only** - the release that made crash telemetry
fully instrumented: it added the faulting-thread backtrace and the access-violation type on top
of the plugin/game version pinned in 1.27.0. Before 1.27.5 crashes were under-reported and carry
no stack/av_type, so restricting to 1.27.5+ keeps the whole crash population consistent (rate,
categories, av_type and stacks all from one set). The rate is expressed **per launch, not per
session**: crashes are always sent but `session_end` is sampled, so launches are the only honest
denominator. Crashes whose host process is dev/replay tooling are excluded too. The threshold is
a single constant (`CRASH_MIN`) - bump it as newer instrumentation lands.
